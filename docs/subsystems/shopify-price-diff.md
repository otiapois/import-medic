# Shopify supplier price diff

The browser and tests call the pure engine in [src/core/shopify-price-diff](../../src/core/shopify-price-diff/index.ts).

- `parseBaseline(bytes, name?)` reads a Shopify product export with current or legacy headings. `parseSupplier(bytes, name, { sheetName }?)` reads a supplier CSV or XLSX and returns worksheets and file-level issues. Passing an exact visible XLSX worksheet name selects that sheet. The selected worksheet carries its own issues. CSV rows use their physical starting lines, including after multiline fields. XLSX rows use the worksheet's original one-based numbers.
- `suggestColumns(baseline, sheet)` returns zero-based candidate indices. Multiple plausible choices or a cost-only suggestion require explicit mapping confirmation. Compare-at is opt-in. `buildPriceDiff(baseline, sheet, selection?, resolutions?)` returns rows, issues, the verified native update and rollback pair when available, and both audit formats. Row resolutions use the supplier's physical row numbers and may provide a skip, a replacement amount, or explicit approval of an exceptional valid amount.
- Identity uses exact SKU text or the exact tuple of handle and option values. The engine reports every row of a duplicate identity. It checks the selected supplier key and any independently identifiable alternate key. Numeric and scientific SKU cells require the original text key. Missing supplier keys can be skipped explicitly. Blank Shopify SKUs remain blank on sibling variants.
- The default guard reviews final retail increases above 200%, drops above 50%, and increases from a zero baseline. A zero, negative, invalid, ambiguous, or spreadsheet-formula-derived supplier amount needs a positive replacement or a skip. Currency symbols, explicit currency columns, and currency-formatted Excel cells require same-currency confirmation when FX is off. Conflicting currency evidence blocks the native pair. Decimal commas with one or two trailing digits are accepted, and ambiguous grouping requires review. Audit delta percentages are displayed to six decimal places.

## Multi-supplier comparison

The comparison accepts one baseline and one to three supplier CSV or XLSX files. Each source has its own filename, label, column mapping, and selected worksheet. The first visible tab is the default. An explicit worksheet choice binds only that supplier slot by exact name. An exact SKU join and an exact handle-and-option join can refer to the same baseline variant. A duplicate identity within a source remains a review issue. Cross-source conflicts retain all contenders' source labels, physical row numbers, and raw cells. The selected source supplies the variant's proposal and is recorded in the diff, CSV or JSON audit, and Client Sign-Off HTML.

The default `block-conflicts` policy holds the native pair when sources disagree. Identical comparable offers can be coalesced when their effective prices and target quantities and compare-at values agree. `prefer-first` and `prefer-last` follow the current order of the source files. `prefer-lowest` and `prefer-highest` compare exact decimal supplier prices in a comparable currency before pricing adjustments. A price tie with different target values still requires a decision. A preference requires confirmation for the current batch. Winning rows must agree on the store currency. Correct independently invalid cells before exporting.

## Inventory quantity

Quantity mapping is optional and starts at **Leave unchanged**. The baseline reader accepts the current `Inventory quantity` heading and legacy `Variant Inventory Qty`. This is Shopify's product CSV quantity field for single-location stores. Multi-location stock uses Shopify's inventory CSV. [Shopify product CSV format](https://help.shopify.com/en/manual/products/import-export/using-csv) · [Shopify location inventory CSV](https://help.shopify.com/en/manual/inventory-and-locations/setup/inventory-csv)

Supplier quantity must be a plain nonnegative whole number. Blank, fractional, negative, formula-derived, and invalid values block the native pair until corrected or skipped. The configurable drop guard defaults to 80% and reviews a drop strictly above the threshold. A transition from positive stock to zero also requires review. The user can approve a valid flagged quantity, enter a replacement quantity, or skip the row. Inventory-only changes count as updates.

## Pricing rules

`selection.pricingRule` applies to the mapped supplier price. Default `direct` with no adjustments preserves the existing direct-price behavior, including precision. Active rules use exact decimal arithmetic.

| Mode | Computation before rounding and minimum retail |
| --- | --- |
| `direct` | Use the supplier amount, converted when manual FX is enabled. |
| `multiplier` | Multiply by `multiplier` and add `fixedFee` when supplied. |
| `percent-markup` | Multiply by `1 + markupPercent / 100`. A negative markup reduces the amount. |
| `target-margin` | Divide by `1 - marginPercent / 100`. The margin must be at least `0%` and below `100%`. |
| `tiered-brackets` | Select the first bracket whose inclusive `upTo` covers the exact post-FX supplier cost. Apply that bracket's multiplier or percentage markup and optional fixed fee. |

The rule uses decimal strings for parameters and the optional `minimumRetail`. The multiplier and minimum must be positive, and the fixed fee must be nonnegative. Active pricing with `none` uses two decimal places and half-up rounding. `ending-99` and `ending-95` select the first matching amount at or above both the exact result and any floor. `nearest-whole` rounds half up to a whole unit, with the smallest whole unit at or above the floor when needed. Invalid parameters block the native pair. Applying a floor requires both the source and calculated amount before rounding to be positive. The fixed fee, floor, and manual row replacements are in store currency. A row override is a final value and bypasses currency conversion and pricing adjustments for that field.

`pricingRule.fx` carries `sourceCurrency`, `storeCurrency`, and `fxRate`. The rate is a positive exact decimal string in store-currency units per source-currency unit. The engine multiplies the supplier amount by that rate using exact rational arithmetic before applying the retail formula, floor, and rounding. Missing or invalid FX settings, currency evidence that conflicts with the selected source currency, and a missing `selection.fxRateConfirmed` block the native pair. Rate input and arithmetic stay local in the browser.

Tiered pricing requires two to six brackets. Every finite `upTo` is a positive decimal string, thresholds strictly increase, and the last bracket uses `upTo: null` to cover higher costs. Multipliers are positive. Tier markup percentages and optional fixed fees are nonnegative. The engine compares exact post-FX cost to the limits before rounding. For limits of `20.00` and `100.00`, the first tier covers `20.00` and the second covers `20.01`. The selected tier applies its own adjustment, then the overall minimum retail and rounding settings apply. Invalid brackets hold the native pair. A label such as `Tier 1 (<= 20.00): 2.5x` appears in the diff, audits, and Client Sign-Off HTML.

## Bundle and kit cost rollup

**Build Update** can attach a separate BOM CSV or an XLSX file with one visible worksheet for base store pricing. Use the headers `Bundle SKU`, `Component SKU`, and `Quantity`, with an optional `Assembly Cost`. Each row names an exact kit-to-component relationship. Preserve leading zeros in both SKU columns and store workbook SKUs as text. Repeat a component within one kit by increasing its positive whole-number quantity on a single row. Assembly is a plain nonnegative store-currency amount in exact cents and applies once per kit. Nonblank entries for the same kit must agree. A blank entry uses the amount declared on another row of the kit, or zero if all of its entries are blank.

The [rollup engine](../../src/core/bom/rollup.ts) evaluates children before their parents and allows up to five kit levels. It adds each component's unit cost in cents multiplied by its quantity, then adds the kit's assembly cost. A sub-kit contributes its new rolled-up cost. Other components use the winning supplier cost when supplied and validated. A component found only in a supplier sheet can contribute a verified cost by exact SKU, including leading zeros. Its supplier row remains unmatched and is omitted from both native CSVs. The existing manual FX confirmation applies to cross-currency supplier costs. A converted unit cost rounds half up once to store cents before quantity multiplication.

If the component is absent from the supplier sheets or its supplier proposal was skipped, the engine can use an explicit baseline cost column such as `Cost per item` and discloses that fallback. Baseline costs must be in exact store cents. A component with no verified cost in either source holds the native pair. The prior kit cost comes from its explicit baseline cost when available, or is rolled up from verified prior component costs with the same BOM. It is unknown when the baseline lacks enough cost data.

The engine applies the confirmed cost-based multiplier, markup, target margin, or tiered rule to the rolled-up cost, then runs the platform's identity, pricing, margin, and native CSV checks. The kit's retail proposal follows the platform's supported native price field. Each kit SKU must match exactly one eligible target row in the baseline. An active supplier proposal for a listed kit or an unresolved choice between confirmed retail rules holds the pair. The pair also stays held if a kit would sell below its rolled-up cost or exceeds the configured price movement guard. Cycles, deeper chains, duplicate component lines, and invalid quantities or assembly costs hold the pair. The cycle diagnostic identifies the affected path and the original CSV lines. XLSX diagnostics use the original worksheet row numbers.

The JSON audit's `bom` section and offline Client Sign-Off show the rollup, component source and source lines, baseline cost when known, new cost, proposed retail, and projected margin when available. `custody.bom` records the exact original BOM file's SHA-256, with worksheet information for XLSX. Holds preserve input fingerprints and review evidence. Both native file digests appear only when the existing local replay verifies the update and the matched rollback. The exported native CSVs carry supported store fields and their original identities. Keep the BOM breakdown with the audit and sign-off.

## Catalog impact and margin

The [shared analytics](../../src/core/analytics/catalog-impact.ts) compare the original and final prices of eligible matched variants using exact arithmetic. For a price movement `x`, the seven buckets are `x < -20%`, `-20% ≤ x < -5%`, `-5% ≤ x < 0%`, no change, `0% < x ≤ 5%`, `5% < x ≤ 20%`, and `x > 20%`. A move from a zero baseline has no percentage. WooCommerce uses regular price for movement.

Gross margin uses `(effective retail - landed cost) / effective retail`, with a WooCommerce sale price taking precedence when present. A cost-based pricing formula or an explicitly cost-labeled direct input establishes the supplier cost. A generic direct price leaves cost unknown. Confirmed FX converts the landed cost exactly. Each calculable variant has equal weight in the mean. The watchlist identifies eligible SKUs whose effective retail is at or below cost.

When inventory mapping is active, the summary reports comparable quantities before and after, their difference, and the count of rows moving from positive stock to zero. Excluded proposals retain their known baseline quantities.

## Margin what-if simulator

[`simulatePriceScenarios`](../../src/core/whatif/simulator.ts) compares up to six distinct scenarios against the same baseline and current single- or multi-supplier setup. It keeps the join, selected price scope, conflict policy, and row resolutions and runs the same native comparison and CSV replay as **Build Update**. A scenario can compound a percentage into the active retail formula before the floor and rounding, multiply an existing confirmed FX rate, or replace the rounding or floor. Source costs use the scenario's FX rate. Manual row overrides still specify final amounts.

`changedSkuCount` counts rows marked Updated by the comparison. `totalRetailDeltaCents` is the sum of proposed effective retail minus baseline effective retail over those rows, as an exact integer string in cents. It is unavailable if an updated row lacks a comparable cent-exact amount, or if the scenario is held. WooCommerce and BigCommerce use the sale price when present. `averageMarginPercent` averages equally across eligible matched rows with known landed cost and positive effective retail, to six decimal places. The result also includes the known-margin count, strictly negative-margin count, count of eligible rows below the selected supplier's floor, and the lowest-margin SKU or row identifier.

Previewing leaves the active batch intact. **Apply Scenario** takes the previewed supplier rules for an eligible changed scenario and reruns the active comparison. Held results and rules with no native update remain unavailable to apply. Check the proposed prices, current file fingerprints, and verified native pair in the same review used for other pricing changes.

Saving an applied percentage adjustment in a supplier recipe retains `retailAdjustmentPercent` in v4 for regular rules, v5 for tiered rules, or v6 for named worksheets. On the next batch, reconfirm any saved FX rate as usual.

## Compare-at pricing

Choose a mapped supplier compare-at column or `pricingRule.compareAtRule` with a decimal `multiplier`. A mapped amount is used directly when FX is off. With FX on, the engine converts that source amount at the same rate and rounds half up to cents. An absent or blank supplier cell retains the baseline value. An automatic rule multiplies the final retail price by its factor and applies the retail rounding setting without the minimum retail floor. This uses the overridden retail price when a row has a retail override. Compare-at overrides are final store-currency amounts.

For a participating row with compare-at enabled, any nonblank final compare-at price must be strictly higher than the final retail price, including after conversion, rounding, or a manual override. The blocking review issue is `compare-at-not-above-price`. Correct the amounts or skip the row. Shopify specifies the same price relationship for sale display. [Shopify sale pricing](https://help.shopify.com/en/manual/products/details/product-pricing/sale-pricing)

## Shopify Markets price scope

Base store pricing is the default. The baseline's `Price / <Market>` headers supply the available market scopes. Shopify exports these fields when a market has exactly one active catalog that it does not share with another market. Match the exact exported price header and its corresponding compare-at header. Review a single scope per batch. For market runs, any manual FX rate is in market-currency units per supplier-currency unit. Apply and confirm it before the pricing formula, fixed fee, floor, and rounding. Manual overrides are final amounts in that market's currency. [Shopify international CSV columns](https://help.shopify.com/en/manual/products/import-export/using-csv#international-csv-columns)

The pair retains exact Shopify identity cells and all original variants of each affected product group. Its only writable fields are `Price / <Market>` and the optional compare-at field for the same market. It omits base prices, stock, `Included / <Market>`, all other markets, and unrelated product content. The market compare-at guard checks original and effective fixed values against their corresponding market prices. Changing between an inherited blank and a fixed value holds the pair because inheritance recovery is unverified. The rollback carries the original cell text, and paired local replay checks exact recovery of the uploaded matrix. Verify the current store, affected groups, fixed prices, and the target market and currency before manually importing the update or its matched rollback. [Shopify overwrite rules](https://help.shopify.com/en/manual/products/import-export/using-csv#overwriting-product-details-using-an-import-csv-file)

## Native CSV pair and audit

The filenames use the Shopify baseline basename with `-price-update.csv` and `-price-rollback.csv`. Both files include the original `Handle`, `Title`, option names and values, and `Variant SKU`. The writable price field is `Variant Price` for the base store or the selected market price header for a Markets run. Shopify requires Handle and Title for product updates and requires the corresponding option fields for variant-dependent updates. Both CSVs contain every variant of each affected product in baseline order, including unchanged and skipped siblings. Linked options require a different workflow. The files omit image-only records and unrelated columns such as Body, Tags, and Image Src. [Shopify product CSV requirements](https://help.shopify.com/en/manual/products/import-export/using-csv#required-columns-in-the-product-csv-file)

Compare-at appears in both native CSVs when a mapping or automatic rule is active. Both require the baseline compare-at column so the rollback can reproduce it for every affected variant. A price-only pair omits the column. The update audit marks each row's compare-at output as `omitted`, `empty`, or `value`. The rollback reproduces the original price and compare-at cell text, including decimal precision and explicit blanks. Unchanged and skipped siblings retain their original values. Shopify's matching-handle overwrite can clear an included blank cell. An omitted optional column is left out of the overwrite. [Shopify overwrite rules](https://help.shopify.com/en/manual/products/import-export/using-csv#overwriting-product-details-using-an-import-csv-file)

In a base-store run, when any supplier has quantity mapping, both native files include `Variant Inventory Qty` and require a baseline quantity column. An affected product group with a malformed nonblank baseline quantity blocks the pair. The update uses the selected supplier's mapped quantity for resolved variants. It retains original quantity for a winning source with no quantity mapping and for untouched siblings. The rollback reproduces the exact uploaded quantity cells, including leading zeros or explicit blanks. With quantity mapping off for every source, the column is omitted from both files.

Before exposing either file, the engine encodes and re-parses the actual UTF-8 output of both files. It overlays the update on the uploaded matrix by exact handle and option keys, checks complete groups and untouched cells, then overlays the rollback and requires exact recovery of the original matrix, including the selected price and quantity cells. `rollbackVerification.restoredVariants` counts the rows carried in the rollback, including unchanged siblings. The verification applies to the matched files and the uploaded snapshot. Shopify imports remain a separate manual action. Check the destination store, included identity fields, prices and quantities, and any later edits or stock movement against the relevant snapshot before either import.

The CSV and JSON audits include statuses, original prices, supplier raw cells, computed and final proposed prices, source rows and columns, resolutions, and local verification for both files. When any row has a landed cost, the CSV adds `Landed Supplier Cost` before the optional `Matched Tier` and `FX Applied` columns. JSON records the row's `landedCost` and structured `fxApplied` when present. For FX runs, the CSV value can be `EUR -> USD @ 1.0850`. `Review and Resolution (JSON)` remains the final CSV column. The Shopify CSV pair carries final store-currency price cells and keeps FX details in the audit. JSON cell payloads in both audits preserve exact values, including leading zeros and the difference between an absent workbook cell and an empty CSV cell. CSV display cells with spreadsheet formula prefixes are escaped. Keep these local audit files with the source data and native pair.

The CSV audit includes `Supplier Source`, `Supplier Filename`, `Supplier Worksheet`, and `Supplier Contenders (JSON)`. The JSON audit includes the chosen supplier's ID, label, filename, and worksheet and competing evidence with source rows and raw cells. A shared issue with more than 40 contenders stores the full list once. Rows that share it carry `supplierContendersIssueIndex` in JSON or `{"issueIndex": …}` in the CSV contender cell. These are zero-based indexes into the JSON audit's `issues` array or the equivalent array in the CSV `Run summary` row's final field. Inventory evidence includes the original quantity, raw supplier quantity, and proposed quantity after any override. Use the audits to inspect the entire run.

The browser worker records SHA-256 of the exact original baseline and supplier file bytes, including the whole supplier workbook in its original XLSX form. The JSON audit adds `custody.baselineSha256` and `custody.suppliers`, with each supplier's `filename`, `sha256`, byte count in `bytes`, and `selectedSheet` after explicit worksheet selection. When the verified native pair is available, the same record adds `updateCsvSha256` and `rollbackCsvSha256` computed from the exact downloadable bytes. Held native files have no output digest. The workbench and Client Sign-Off HTML footer show the same fingerprints and identify the explicitly selected worksheet. The CSV audit keeps its existing column layout.

The Client Sign-Off HTML includes the catalog impact summary, supplier breakdown, and inventory changes. Its detailed comparison shows at most 500 updated or blocked rows, with blocked rows first. The average proposed price change uses updated variants with a comparable baseline price. The worker generates the standalone file with escaped values, inline print styles, and a CSP that blocks scripts and network connections. The report can be downloaded for review while the native CSVs are held.

`selection.formulaGuard` opts into checking native Shopify output for formula-leading text before export. If an outgoing native cell would need an apostrophe, the pair is blocked. The audit records the original baseline line, column, and exact proposed before/after text under `formulaGuard.blocked`. `formulaGuard.neutralized` remains empty for native Shopify exports because their fields must stay exact. The audit CSV independently guards its display fields. In both audits, row entries for multi-row diagnostics point to the zero-based index of the complete issue in the run summary. This keeps all source line numbers without repeating the full list for every affected variant.

## Verify Before Import

The standalone inspector compares an original Shopify, WooCommerce, or legacy BigCommerce export and one candidate native CSV. It fingerprints the exact original bytes with SHA-256, checks supported native columns and required identity values, and reports lexical before-and-after price and stock cells and affected SKUs. For example, `20.00` and `20.000` are different cell values even when they represent the same amount. Forbidden columns, unstable SKU text, or broken groups produce `FAIL_UNSAFE`. Shopify candidates must retain the required identity cells and complete affected variant groups. A Markets candidate selects its scope through its exact exported price header and must stay within that scope. WooCommerce and legacy BigCommerce candidates must match the existing row identities and relationships. [WooCommerce native scope](woocommerce-price-diff.md#native-pair) · [BigCommerce native scope](bigcommerce-price-diff.md#native-pair)

With only a baseline and candidate, the inspector can confirm exact agreement for included scoped cells. Full recovery uses the verified, matched update as a third input. The verifier applies that update to the original catalog data, applies the rollback, and checks the resulting cells throughout the original matrix. The standalone baseline check concerns the supplied file, and the paired replay concerns the supplied update and rollback. Store import and verification of the current catalog are manual steps.

For a Sale Campaign Pack, use Promo Launch as the update and Promo End Revert as the rollback. WooCommerce and legacy BigCommerce campaign candidates can carry sale prices alone, alongside their required identity columns. [Campaign field and clear rules](promo-campaign.md#native-csv-scope)

## Supplier recipes and local worker

[`SupplierRecipe`](../../src/core/shopify-price-diff/recipe.ts) is strict UTF-8 JSON with a supplier label, exact headers for the selected SKU or handle/option key, price and optional compare-at columns, worksheet information, movement thresholds, and formula guard setting. Version 1 loads in direct-price mode. Version 2 carries `pricingRule` and optional `storeLabel`. Version 3 adds manual FX or the automatic compare-at rule. Version 4 supports the supplier's optional inventory header, stock drop threshold, and conflict policy. Version 5 extends the v4 fields and requires a tiered pricing rule. Version 6 binds an explicit worksheet selection and requires `selectedSheet` and `sheetName` to hold the same exact name. An FX recipe requires top-level `fxRateNeedsRecheck: true`. Column, conflict-policy, currency, and FX confirmations and row decisions stay with the current batch. Import accepts versions 1–6 and rejects unsupported versions, unexpected or duplicate properties, unsafe text, and overlapping roles. Applying checks the exact worksheet and headers in the current batch and supports column reordering. Remap missing or ambiguous names and reconfirm the restored settings before export. Reverify any carried FX rate for the new batch.

The [module worker](../../src/core/worker/diff.worker.ts) reads and parses the baseline and supplier files, runs the comparison, and holds full cells and audits in worker memory. It reports progress at row or group checkpoints during joins and native CSV replay and yields between batches of result indexing. The UI receives counts and paginated reviews, including SKU and handle search. The CSV audit serializes up to 1,024 records at a time. The JSON audit uses compact formatting above 10,000 diff rows. Native CSV, audit, and sign-off downloads are prepared in the worker and sent as a transferable buffer per request. Only the current run can deliver its result or download.

## XLSX input

The workbook reader uses the pinned MIT packages fflate and fast-xml-parser for ZIP and XML parsing. The pure `listWorkbookSheets(bytes)` API returns visible worksheet names in workbook order. The reader accepts standard worksheet values and text, including inline, shared, and rich text strings. It warns when a formula has no cached value and never evaluates formulas. Formula-derived fields used for supplier identity, price, or quantity still require review. The reader rejects DTD/entity declarations, external workbook relationships, macro-enabled workbooks, duplicate headers, and worksheet rows that place data beyond the header range. Limits are 16 MiB input, 64 MiB declared expanded data, 512 archive members, 32 sheets, and 400,000 populated cell records across the workbook.

The synthetic agency demo and regressions live under [fixtures/shopify-price-diff](../../fixtures/shopify-price-diff). The workbook fixture has two worksheets and sparse rows. The [Vitest suite](../../tests/unit/core/shopify-price-diff.test.ts) executes the original CSV and XLSX bytes and re-parses actual generated bytes. `npm run test:fuzz` repeats fixed-seed cases for parsing, joins, supplier conflicts, pricing rules, optional inventory, native CSV replay, recipes, guard behavior, and repairs.
